# commercetools B2C Storefront

A Next.js (App Router) B2C storefront connected to commercetools, covering:

- Home page
- Product listing (PLP) with facets, powered by the **Product Search API**
- Product detail page (PDP)
- Cart
- Checkout via the **Checkout Browser SDK** (full hosted `checkoutFlow`)
- Customer authentication (register/login/logout) and an account area
  (profile, addresses, order history)
- Search page
- Wishlist pages and heart-save actions (PLP/PDP)

## Getting started

1. Copy `.env.example` to `.env.local` and fill in your commercetools project
   credentials (see [Environment variables](#environment-variables) below).
2. Install dependencies and run the dev server:

   ```bash
   npm install
   npm run dev
   ```

3. Open [http://localhost:3000](http://localhost:3000).

## Environment variables

See `.env.example` for the full list. Key ones:

| Variable | Purpose |
| --- | --- |
| `CTP_PROJECT_KEY`, `CTP_CLIENT_ID`, `CTP_CLIENT_SECRET`, `CTP_AUTH_URL`, `CTP_API_URL` | commercetools project credentials, server-side only. |
| `CTP_SCOPES` | OAuth scopes requested for the shared client-credentials token (see [Architecture](#architecture--session-model) below for why these are admin-level scopes). |
| `CRON_SECRET` | Secret used to authorize the scheduled Sale-category synchronization endpoint. |
| `CTP_CHECKOUT_APP_KEY` | Key of the Checkout Application configured in Merchant Center under *Settings > Checkout > Applications*. Must be updated to your real application key before the checkout flow will work. |
| `SESSION_SECRET` | Symmetric key used to encrypt the session cookie (`jose`). Generate with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. |
| `DEFAULT_CURRENCY` | Fallback currency when a locale isn't in `COUNTRY_CONFIG`. |

## Architecture & session model

This storefront uses a **single shared, admin-scoped, client-credentials
API client** for every commercetools call — catalog reads *and* cart/customer/
order mutations. There is no per-shopper OAuth token flow and no `.me()`
endpoints.

**Why:** commercetools's typical storefront pattern uses a password/anonymous
OAuth flow with `manage_my_*` scopes so each shopper's browser effectively
holds their own token and calls `.me()` endpoints. That requires the API
Client (in Merchant Center) to have `manage_my_profile`, `manage_my_orders`,
`manage_my_business_units`, etc. enabled. If your API Client is configured
with only admin-level scopes (`manage_orders`, `manage_customers`, ... but no
`manage_my_*` scopes), the `.me()` endpoints will always fail with
`insufficient_scope`.

To support that common setup out of the box, this app instead:

- Keeps one shared `ApiRoot` (see [lib/ct/client.ts](lib/ct/client.ts)),
  authenticated via client-credentials with the scopes in `CTP_SCOPES`.
- Tracks shopper identity in an encrypted session cookie
  (`ct_session`, see [lib/ct/session-cookie.ts](lib/ct/session-cookie.ts))
  containing `{ anonymousId, customerId?, email?, cartId? }` — `anonymousId`
  is a UUID generated by this app (not a commercetools anonymous session token).
- Uses the **plain** (non-`.me()`) REST endpoints with explicit
  `anonymousId`/`customerId` filtering:
  - Carts: `POST /{projectKey}/carts` with an explicit `anonymousId`, looked
    up later via `cartId` in the cookie or a `where anonymousId=... or
    customerId=...` query ([lib/ct/cart.ts](lib/ct/cart.ts)).
  - Signup: `POST /{projectKey}/customers` (`CustomerDraft` supports merging
    in the anonymous cart via `anonymousCartId`/`anonymousId`).
  - Login: `POST /{projectKey}/login` (`CustomerSignin` also supports the
    anonymous cart merge).
  - Profile/address/order history: admin-scoped
    `.customers().withId(...)` / `.orders()` with a `where customerId=...`
    filter ([lib/ct/customer.ts](lib/ct/customer.ts)).
  - B2B quote requests: as-associate, Business Unit-scoped quote request,
    quote, and order reads; the API Client needs `view_business_units`,
    `view_quote_requests`, `view_quotes`, and order access (`view_orders` or
    `manage_orders`) scopes.

If your API Client **does** have `manage_my_*` scopes and you'd prefer the
standard per-shopper OAuth pattern, swap `lib/ct/client.ts`/`session.ts` for
a password-flow client and switch the calls in `lib/ct/cart.ts` /
`lib/ct/customer.ts` back to their `.me()` equivalents.

## Product Search API notes

- [lib/ct/product-search.ts](lib/ct/product-search.ts) queries
  `POST /{projectKey}/products/search`. Unlike Product Projection search,
  this endpoint does **not** accept a `published` field filter — it always
  searches the currently published product data implicitly.
- Facets are requested optimistically: category facets (`categories.id`,
  always valid) plus attribute facets defined in `FACETABLE_ATTRIBUTES`
  (`color`, `size`, `brand` by default). If your project's product type
  doesn't have matching attributes, the search call automatically retries
  with fewer facets rather than failing outright — update
  `FACETABLE_ATTRIBUTES` to match your actual product type's attribute names
  once you have a real catalog loaded.

## Checkout

Checkout uses `@commercetools/checkout-browser-sdk` in full hosted
`checkoutFlow` mode. [app/api/checkout/session/route.ts](app/api/checkout/session/route.ts)
creates a Checkout Session (commercetools Sessions API) for the current
cart, and the checkout page mounts the Checkout Browser SDK widget with that
session. You'll need to:

1. Configure a Checkout Application (and a PSP connector, e.g. Stripe) in
   Merchant Center.
2. Set `CTP_CHECKOUT_APP_KEY` to that application's key.

## Scripts

- `npm run dev` — start the dev server.
- `npm run build` — production build.
- `npm run lint` — ESLint.
- `npm run setup:category-fields` — idempotently create the commercetools
  `category-storefront-fields` Custom Type and its optional `imageUrl` and
  `showInNavigation` storefront fields. The API Client must have the
  `manage_types` scope.
